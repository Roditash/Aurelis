# AURELIS — MASTER PROJECT SPECIFICATION

> **Project codename:** AURELIS  
> **Core concept:** A cross-disciplinary interactive laboratory for exploring emergence, causality, adaptation, feedback, and complex systems.  
> **Primary goal:** Create a virtual experience that is immediately fascinating to non-experts while containing enough technical and scientific depth to impress specialists.  
> **Target:** University achievement / innovation fair.  
> **Format:** 100% virtual/software.  
> **Development window:** September 12, 2026 → September 25, 2027.

---

# 1. NON-NEGOTIABLE PROJECT VISION

AURELIS must NOT become a conventional website, CRUD application, generic educational platform, simple simulator, or ordinary game.

AURELIS must feel like:

> **A digital universe where people can experiment with complex systems and discover behaviors they did not explicitly program.**

The visitor should understand the experience within seconds:

> **“I change something. The world reacts. Unexpected behavior emerges. I can investigate why.”**

The deeper layer should reveal serious engineering, mathematics, computation, visualization, simulation, data analysis, and systems thinking.

The project must have two simultaneous levels:

### Layer A — Public / intuitive

A person with no technical background can:

- Enter a beautiful interactive environment.
- Manipulate a small number of intuitive variables.
- Watch the system evolve.
- Observe surprising outcomes.
- Compare experiments.
- Understand the basic story without reading technical documentation.

### Layer B — Expert / technical

A technical visitor can investigate:

- The underlying rules.
- State transitions.
- Feedback loops.
- Dependencies.
- Emergent behaviors.
- Simulation statistics.
- Performance.
- Reproducibility.
- Internal architecture.
- GPU/CPU workloads.
- Data generated by experiments.
- Algorithms and numerical methods.

**Both layers must be part of the same product.**

Do NOT build a simple interface first and then attach “technical features” afterward.

---

# 2. CENTRAL QUESTION

Everything in AURELIS must reinforce one central question:

> **How can simple rules produce complex behavior?**

Secondary questions may include:

- What happens when one variable changes?
- Why does a system become stable or unstable?
- How does feedback amplify or suppress change?
- When does adaptation emerge?
- How can a tiny local event create a large global effect?
- How can two almost identical initial conditions produce very different outcomes?
- Which patterns can be discovered from repeated experiments?

These questions define the identity of the project.

---

# 3. THE CORE EXPERIENCE

AURELIS is an experimental digital world.

The user does not simply “watch” a simulation.

The user:

**OBSERVE → MODIFY → RUN → DISCOVER → INSPECT → COMPARE → REPEAT**

The system should make experimentation feel natural.

A typical session should look like:

1. Enter a world.
2. Observe its current state.
3. Select one or more controllable variables.
4. Modify a condition.
5. Start the experiment.
6. Watch the world react in real time.
7. Detect an unexpected pattern.
8. Pause or slow the simulation.
9. Inspect the relevant chain of events.
10. Create a second experimental branch.
11. Change one condition.
12. Run both branches.
13. Compare results.
14. Determine what changed and why.

This is the fundamental loop.

# 10. BRANCHING / A-B EXPERIMENTS

A signature feature should be experimental branching.

Example:

### Experiment A

Initial condition:

- Variable X = 50
- Variable Y = 20

### Experiment B

Same initial state except:

- Variable X = 51

Run both.

AURELIS should make the divergence visible.

The user should be able to inspect:

- When the branches began diverging.
- Which events caused the divergence.
- Which feedback loops amplified it.
- Final differences.
- Quantitative metrics.

This should become one of the project's strongest demonstration features.

---

# 11. CAUSAL / EVENT VISUALIZATION

When an important event occurs, the user should be able to inspect it.

Example structure:

**Event A**

↓

causes

**Event B**

↓

changes

**Variable C**

↓

triggers

**Event D**

↓

produces

**Global outcome**

This visualization should never claim scientific causality unless the model actually supports that interpretation.

Use precise language such as:

- “preceded by”
- “influenced by”
- “dependency”
- “propagation”
- “model relationship”

unless true causal inference has actually been implemented and validated.

# 14. TECHNOLOGY PHILOSOPHY

Technology must be selected **after understanding the problem.**

Never select a technology because:

- Its name sounds impressive.
- It is trending.
- It is difficult.
- It is unfamiliar.
- It appears on a “best tech stack” list.

Every significant technology must answer:

1. What problem does it solve?
2. Why does AURELIS need that problem solved?
3. Why is this technology appropriate?
4. What simpler alternative was considered?
5. What engineering advantage does it provide?
6. What complexity does it introduce?
7. Is that complexity justified?

If the answer is weak, remove the technology.

# 16. TECHNOLOGY STACK RULE

Prefer this logic:

**Problem → Requirement → Engineering constraint → Technology**

Never:

**Technology → Find a place to use it**

For example:

If the project requires thousands of calculations per frame:

→ GPU compute becomes relevant.

If native-speed deterministic computation is required in the browser:

→ Rust + WebAssembly becomes relevant.

If large experiment datasets need local interactive analysis:

→ DuckDB becomes relevant.

If real-time binary transport is required:

→ Protobuf + an appropriate transport becomes relevant.

Every technology must have this type of justification.

# 19. DATA REPRODUCIBILITY

Where randomness exists, experiments should support explicit seeds.

A saved experiment should contain enough information to reproduce it.

The goal:

> Same configuration + same seed + same simulation version = reproducible result, within documented numerical constraints.

This is an important expert-facing feature.

# 32. DEFINITION OF “ADVANCED”

An advanced technology is valuable only when it enables something materially better.

Good:

> Rust + WebAssembly because the simulation core needs high-performance deterministic computation in the browser.

Bad:

> Rust because Rust is advanced.

Good:

> WebGPU because thousands of independent simulation calculations can be parallelized.

Bad:

> WebGPU because it looks futuristic.

This distinction is mandatory throughout the project.
